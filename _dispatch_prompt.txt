GUI cleanup pass on the Aura main window. Functional behavior stays intact — this is visual and layout only, no semantic changes to what the controls do.

Read first:
- The PySide6 GUI module (probably aura_harness/gui/ or aura_harness/ui/ — find it). Read every file that composes the main window.
- Understand the semantics of each control before changing it: what the Planner text area does, what the second text area at the bottom does (currently "Describe what you want built..."), what the two Send buttons each trigger, what "Commit Generate" does, what the Validation checkbox toggles, what the two model dropdowns each control, what the N: spinner is for, what the file-list checkboxes in the workspace sidebar do, what the "..." and partially-visible "Ne[w]" buttons next to the workspace path do.

Problems to fix:

1. The QGroupBox treatment with the cyan/teal border and the tiny label overlapping the top edge ("Planner", "Validation") looks dated and hard to read. Replace with a cleaner section style — a regular bold label above each section, separated by subtle spacing or a thin horizontal rule. Drop the box borders entirely on these sections.

2. The two text input areas have similar vague placeholders ("Describe what you want to plan..." and "Describe what you want built..."). The visual treatment doesn't communicate that one is for the planner and one is for the worker (or whatever the actual semantics are — figure out from the code). Re-label both inputs with concrete labels above them describing what each input drives, and what stage of the pipeline runs when its Send button is clicked. Same for the two model dropdowns — each should have a label like "Planner model" / "Worker model" (or the accurate names based on code semantics).

3. The two Send buttons need distinct labels matching what each does. If one runs the planner and the other runs the worker, label them "Run Planner" and "Run Worker" (or whatever the accurate verbs are based on the code). "Send" twice is meaningless.

4. "Commit Generate" — figure out what this does from the code and rename to something readable. If it commits the plan and triggers generation, "Commit & Generate" or "Approve Plan" or whatever fits.

5. The Validation section as drawn is just a thin strip with a single checkbox and an empty area below it. Either: (a) if validation has real controls/output, lay them out properly with adequate vertical space; (b) if it's just a toggle, fold the checkbox into the worker section as a single labeled checkbox row, drop the standalone section.

6. The workspace sidebar header gets truncated — the path "C:\Projects" runs into the "..." button and partially shows "Ne" of what's probably a "New" button. Lay out the header so the path has its own row (truncated with ellipsis if too long, with the full path on hover via tooltip) and the action buttons are on a second row or arranged so neither clips the other.

7. The empty middle area between the Planner section and the Validation section — figure out what it's for from the code (output display? plan preview?). Give it a label so its purpose is visible even when empty, and a placeholder/empty-state message ("Plan output will appear here" or similar based on actual purpose).

8. General consistency: use the same padding/margins across all sections, consistent button heights, consistent font sizes for labels vs. inputs vs. body text. Right now the visual weight is uniform across everything which kills hierarchy.

Visual direction:
- Keep the dark theme — don't switch to light.
- Drop the heavy cyan accents on borders. Reserve accent color for primary action buttons only (e.g. the main "Run Planner" / "Run Worker" Send buttons, kept blue) and maybe focus rings on inputs.
- Section dividers should be subtle — either thin neutral-gray horizontal rules or just whitespace.
- Inputs (QLineEdit, QPlainTextEdit) get a 1px subtle border, slightly lighter background than the window, comfortable internal padding.
- Bold labels for section headers, regular weight for inline labels next to dropdowns/checkboxes.
- Buttons: primary action filled blue, secondary actions outlined or flat.

Implementation:
- Most of this is layout (QVBoxLayout / QHBoxLayout / QFormLayout adjustments) plus a Qt stylesheet (QSS). Prefer adjusting layouts and using a single coherent QSS block applied at the window level over per-widget setStyleSheet calls.
- Don't introduce new widget libraries. Native Qt widgets with QSS only.
- Don't change any signal/slot wiring. Don't rename methods. Don't change any state model. Pure visual + layout + labels.
