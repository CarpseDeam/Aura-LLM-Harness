aura_harness/stations/planner.py

PlannerStation class. Constructor:
- name: str = "planner"
- backend: Backend
- model: str — caller passes the model string (e.g. "deepseek-v4-flash" for cloud, "gpt-oss:20b" for local)
- temperature: float = 0.2
- max_parse_retries: int = 1

Signature:
- run(task_spec: TaskSpec) -> Plan

Internal flow:
1. Render the planner prompt from task_spec.description (and any other relevant TaskSpec fields). Use the prompt template file (see below).
2. Call backend.chat() with messages=[{"role": "system", "content": <planner system prompt>}, {"role": "user", "content": <rendered task>}], response_format={"type": "json_object"}, temperature, model. response_format is a no-op on LocalOllamaBackend (per dispatch 1) and the prompt itself has to coerce JSON output for the local path; that's expected and the prompt should be written to work either way.
3. Parse the response text as JSON. On parse failure: retry up to max_parse_retries times by appending a follow-up user message {"role": "user", "content": <parse error feedback, asking for valid JSON only>}. After retries exhausted, raise BackendError with the last parse error.
4. Validate the parsed JSON against the Plan/Slice schema:
   - Top-level object has a "slices" array with at least one entry.
   - Each slice has the fields the dataclass requires (id, description, target_path, contract.expected_symbols, contract.forbidden_imports).
   - Slice ids are unique.
   - Validation failures get one retry the same way parse failures do (feedback message → re-call). After exhaustion, raise.
5. Construct frozen Plan / Slice / SliceContract dataclasses from the validated JSON.
6. Stamp genealogy on the Plan: produced_by_station="planner", produced_by_backend=self.backend.name, produced_at=<datetime, matching the convention used elsewhere>, seed=None, input_ref=task_spec.id (or whatever the TaskSpec identifier field is — use the actual field name from types.py).
7. Return the Plan.

Plan-level critic is explicitly out of scope. Don't add hooks for it. Keep the return type `Plan`, not `Plan | CritiqueReport`. When plan-level critic lands later, we'll change the signature then.

aura_harness/stations/prompts/planner.md (or .txt — match whatever convention exists; if no prompts directory exists yet, create it)

The system + user prompt template the station renders. Two sections in the file separated by a clear marker the loader can split on (e.g. `---SYSTEM---` and `---USER---`, or just two files `planner_system.md` and `planner_user.md` — your call, pick the one that fits the existing repo patterns better).

The system prompt establishes:
- The role: "You are a software planner. You decompose a task into a small number of slices (typically 2-5 for small projects). Each slice produces one source file."
- The output contract: must return a single JSON object matching the Plan schema. Include a literal example of the expected JSON structure with all fields populated for a trivial sample task. The example is the schema specification — make it accurate to the dataclasses.
- Slice quality bar: each slice has a clear single responsibility, expected_symbols lists the public functions/classes the file must expose, forbidden_imports lists modules the file must not import (use this to enforce module boundaries — e.g. a "render" slice forbids importing from a "physics" slice's file, etc.), target_path is a relative path from the workspace root.
- Compositional constraint: the slices, when implemented and combined, must produce a runnable program. Order of slices is execution order. Later slices may import from earlier slices' target_paths but not vice versa.
- Style direction: prefer small files, one class or one logical unit per slice, no slice should be more than a few hundred lines of code.

The user prompt template renders task_spec.description and any other relevant TaskSpec fields. Keep the user prompt minimal — the system prompt does the heavy lifting on schema and quality.
