## Goal
Restructure the bench runner from per-candidate orchestration to phase-based orchestration. Currently `_resolve_candidate_slot` runs each candidate's full lifecycle independently, which means the runner swaps models (coder → critic → coder → critic → ...) per-candidate. With ~25 candidates × 2 critic rounds and ~10s per swap, that's ~25 minutes of wall time spent on swap overhead per bench run. Phase-based orchestration cuts this to roughly 6 swaps total.

## The phase pipeline
For a single run (one batch of N candidates with K critic rounds):

1. **Phase: round-0 generation.** Coder loaded. Generate all N candidates in parallel (already parallel via ThreadPoolExecutor in CandidateGenerator). Verify each.
2. **Phase: critic round 1.** Coder unloaded, critic loaded. Critique all candidates that failed round 0, in parallel against the loaded critic model.
3. **Phase: retry round 1.** Critic unloaded, coder loaded. Generate retries for all candidates that got actionable critiques, in parallel. Verify each.
4. **Phase: critic round 2.** Same as phase 2 for any candidates still failing.
5. **Phase: retry round 2.** Same as phase 3.
6. End-of-run unload.

Each phase: "load model X, do all the work that needs X, unload X." Within a phase, work is parallel.

## Critic parallelism
The critic is currently called serially. With phase-based orchestration, multiple critic calls can run concurrently against the loaded critic model. Use ThreadPoolExecutor — same pattern as CandidateGenerator. Default to 4 workers, configurable via a constant.

## Ratchet logic preservation
The ratchet (one-way fitness valve) MUST be preserved. The change is *when* and *how* work is scheduled, not the decision logic.

Per-candidate state across phases: each candidate has a "prior-best" round. The retry's prior_code in its prompt is always the prior-best's code. After a retry phase, evaluate each retry: did tests_passed strictly improve over that candidate's prior-best? If yes, retry becomes new prior-best. If no, prior-best stays unchanged. Same logic as today, just batched per phase.

## Termination per candidate
A candidate exits the pipeline (excluded from further phases) when:
- Its prior-best passes (tests_passed == tests_total).
- We've done all critic_rounds retries.
- The most recent critique returned no actionable violations.
- Code extraction fails on the prior-best.

Track with an "alive" flag per candidate. Phase 2 only critiques alive candidates. Phase 3 only retries candidates with actionable critiques.

## Files to change
- `src/aura_harness/bench/runner.py` — the heart of the refactor. `_resolve_candidate_slot` either gets restructured into phase functions or replaced by a `_resolve_batch_phases` style function. Existing helpers (`_verify_candidate_round`, `_build_reflexion_prompt`, `_read_gradient_report`) should be reusable.
- Possibly small updates to `CriticClient` if a batch entry point feels cleaner — or just call from a ThreadPoolExecutor without changes.

## Constraints
- All existing JSONL output fields must be preserved. The `rounds` list per candidate must still contain every round (including ratchet-rejected retries) in chronological order, with the same fields it has today.
- `unload_model` calls land at phase boundaries, not per-candidate. The per-candidate unload wiring from the earlier dispatch needs to be removed/relocated as part of this refactor.
- Progress logging continues to work — emit phase-level events like `[run 1/5 phase: critic round 1] critiquing 8 candidates` and per-candidate completion events within phases.
- Best-effort progress.json updates throughout.

## Performance expectation
A `--runs 5 --n 5 --critic-rounds 2` run should drop from ~70 min to ~40-50 min. If it doesn't, something's wrong with the phase boundaries or the unload calls.

## Definition of done
- `python -m aura_harness.bench --task duplicate_finder --runs 1 --n 3 --critic-rounds 2 --critic-model deepseek-r1:14b` runs to completion.
- Session JSONL is structurally identical to current output.
- Pass rates on duplicate_finder remain in the same ballpark as run-000 (76% with critic rounds, ~24% one-shot). Significant deviation is a regression.
- All 68 existing tests still pass.
