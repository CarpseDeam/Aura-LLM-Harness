## Goal
Add explicit model unloading to the bench runner so only one Ollama model is resident in VRAM at any given moment. We have a 16GB VRAM ceiling and the current setup spills the 7B coder + 14B critic into system RAM, dropping generation throughput by ~10x.

## Files to change
- `src/aura_harness/llm/ollama_client.py` — add `unload_model(model_name: str)` method.
- `src/aura_harness/bench/runner.py` — call unload at three points (described below).

## New file
- `scripts/verify_unload.py` — a small standalone script that exercises the unload path and reports whether VRAM was actually freed. Not a pytest; meant to be run once manually after this dispatch lands.

## OllamaClient.unload_model behavior
- Sends `POST /api/generate` with body `{"model": "<name>", "prompt": "", "keep_alive": 0}`.
- This is Ollama's documented "evict now" pattern: empty prompt + `keep_alive: 0` triggers eager unload without generation.
- Use the existing `_post_json` helper. Use the existing timeout.
- On success, log to the existing JSONL call log with a synthetic record (model name, `event="unload"`, no eval counts). Reuse `_log_call` if it fits cleanly; otherwise add a sibling `_log_event` method — your call.
- On `OllamaError`, log the error but do NOT re-raise. Unload is a best-effort throughput optimization, not a correctness requirement. If Ollama is unreachable the next real call will fail loudly anyway and that's the right place for the error to surface.
- Returns `None`.

## Runner integration
In `bench/runner.py`, the invariant we want: at any moment during a run, exactly one model is resident.

Three unload points, all in `run_bench`:

1. **After each `generator.generate(...)` call finishes**, before the critic might be invoked. This applies to both the round-0 batch generation and the round-N+1 retry generation in `_resolve_candidate_slot`. Unload the coder `model`.

2. **After each `critic.review(...)` call finishes**, before the next coder generation. Unload the `critic_model`.

3. **At the end of `run_bench`**, after `write_summary` — unload whichever model was most recently used. This leaves the GPU clean for the next process.

The unloads in `_resolve_candidate_slot` are the tricky ones because that function runs per-candidate and currently does generation + critique + generation tightly coupled. Two options:
- (a) Unload inside `_resolve_candidate_slot` between each generate/critique pair. Many small unloads but invariant holds tightly.
- (b) Restructure so that each round happens batch-wide instead of per-candidate — generate all retries together, critique all failures together. Bigger refactor but matches the "phase-structured pipeline" architecture better.

**Pick (a) for this dispatch.** (b) is a bigger architectural move that we'll do separately. The goal here is correctness of VRAM management, not pipeline restructuring.

Note that (a) means a lot of swap overhead per candidate (~10s per swap × multiple swaps × N candidates × rounds). That's acceptable for now because the alternative is silent spillover. We'll measure and optimize after this lands.

## Verification script (`scripts/verify_unload.py`)
Standalone script, runnable from the project root via `python scripts/verify_unload.py`. It should:

1. Load model A (e.g. `qwen2.5-coder:7b`) by issuing a tiny `generate("hello", num_predict=1)`.
2. Query `GET /api/ps` to confirm model A is loaded. Print the response.
3. Call `client.unload_model("qwen2.5-coder:7b")`.
4. Wait briefly (~2s) for eviction to settle.
5. Query `GET /api/ps` again. Confirm model A is no longer in the list. Print the response.
6. Print PASS or FAIL based on whether the model disappeared from `/api/ps`.

The script is the user's tool for confirming the wiring works on their actual hardware. Keep it simple, no fancy CLI args, hardcode the model name.
