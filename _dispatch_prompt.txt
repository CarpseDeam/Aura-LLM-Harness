## Spec: Chat-style planner layer

Add a conversational planning step in front of the existing one-shot prompt → N candidates flow. The user will chat with a planner model to converge on what to build; in a future dispatch we'll wire "Commit & Generate" to spec extraction → decomposition → CandidateGenerator. This dispatch is the chat-only piece.

**File layout:**

`src/aura_harness/planner/__init__.py` — exports for the package.

`src/aura_harness/planner/conversation.py` — Pure data layer. Frozen dataclasses for a single turn (role, content, timestamp) and for the whole conversation state (session id, model, system prompt, tuple of turns). Provide an immutable "appended" method for adding a turn. No I/O, no Ollama, just data.

`src/aura_harness/planner/planner_client.py` — Stateless service that takes a ConversationState and returns the next assistant turn from Ollama's chat endpoint. Mirror the shape of `aura_harness/llm/OllamaClient`: same constructor pattern, same JSONL logging style, same conventions. Compose with OllamaClient where reasonable; otherwise add a sibling chat method on it. Streaming is desired if it can be added without significantly restructuring the existing client; if not, block-and-return is fine for v1.

Define the planner system prompt as a module-level `Final[str]`. Frame the model as a conversational collaborator — asks clarifying questions, surfaces assumptions, helps shape a clear spec, doesn't generate code. Keep it short; we'll iterate on it.

`src/aura_harness/ui/planner_worker.py` — `PlannerWorker(QThread)` mirroring the existing `BatchWorker`. Emits a signal on success with the new turn, a signal on error.

`src/aura_harness/ui/planner_widget.py` — `PlannerWidget(QWidget)` owning the planner conversation UI: scrollable transcript with user/assistant turns rendered as distinct visual blocks (plainer than candidate cards — this is conversation, not code), a planner-specific input box with Send button and Ctrl+Enter shortcut, a model dropdown populated from `OllamaClient.list_models()`, and a "Commit & Generate" button that's enabled once there's at least one assistant turn. The widget owns its `ConversationState` internally. Exposes a `commit_requested` Qt signal carrying the committed state. Use the existing `theme` module for styling.

`src/aura_harness/ui/main_window.py` — Embed `PlannerWidget` into the right column above the existing output area, in its own visually-clear region. The existing candidate-generation flow stays unchanged. Connect `commit_requested` to a stub handler that logs the committed state — real wiring to extractor → decomposer → CandidateGenerator is the next dispatch.

`src/aura_harness/__main__.py` — Instantiate `PlannerClient` and pass it through to `MainWindow` alongside the existing collaborators.

**Conventions:**

Match the existing codebase: `from __future__ import annotations`, type hints throughout, frozen dataclasses for value types, `Final[...]` module-level constants for any tunables (no magic numbers in function bodies), JSONL logging via the existing logger pattern. Mirror the idioms already established in `lab/`, `scoring/`, `scaffold/`, and `ui/`. The planner model dropdown is separate from the candidate-generation model dropdown.

**Definition of done:**

User can launch the harness, type into the planner widget, send, see the planner reply rendered in the planner transcript, and continue the conversation across multiple turns with history maintained. "Commit & Generate" is clickable and fires the signal (handler is a stub that logs). The existing candidate-generation flow still works unchanged. Business logic lives in the planner package and the planner widget; `MainWindow`'s additions are limited to instantiation and signal routing.

Be methodical. Read what you need, make the change, stop. Match existing code style. Type hints everywhere.
